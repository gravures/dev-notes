## What we actually know (facts, not theories)

- Regression is attributable to **Task 1 and/or Task 2** (user assertion).
- **Task-2-specific fact (strongest concrete suspect):** the kitty graphics spec
  (`t=s` shared-memory transfers) says *the terminal must read the data from the memory object and then **unlink and close** it*. Pre-Task-2, every `write()` re-did `shm_open(O_CREAT)+ftruncate+mmap`, so the name was recreated each paint after the terminal consumed/unlinked it. Post-Task-2, `ensure_mapped` creates the mapping once and never recreates the name → after the terminal unlinks following the first read of a given buffer, **every later transfer of that buffer fails** (stale/frozen fragments — matches "partially unaligned image buffer"). Old code's ftruncate used the constructor size, so size-mismatch failure semantics were unchanged by Task 2; the unlink/recreate behavior *is* a Task-2 behavior change.
- **Task-1-specific fact:** dirty writes now assume the SHM holds the previous full frame and that the Electron `image` is whole-frame with `dirty` in image device-pixel coords. If either assumption is wrong at runtime, partial updates corrupt the frame. `clampedDirtyRect()` clamps to `imageSize`; a full-cover dirty falls back to undefined (= full write).
- Native conversion: `bgra_to_rgba` requires exact `src.len() == dst.len()` (full path);`bgra_to_rgba_rect` validates `src` bounds + `dst` rect size and packs **at dst origin**
  — Task 2's `write()` slices dst to `dst_start..dst_end` so rect writes land at their true frame offset.
- Ctrl-C is bound (`<C-c>` → `process.emit('SIGINT')` → `cleanup(0)` in `src/index.ts`); its failure is a side-effect of the main bug per the user.
- No Rust writer is used in the non-tmux JS path (`write_maybe_tmux` has no callers in `src/`); graphics output goes through JS `process.stdout` only.
- `X=/Y=` in the kitty protocol are **pixel offsets within the cell** (spec-verified) — the fallback's sub-cell placement math is semantically correct.
